# Боевой тест: способна ли локальная модель быть junior-помощником senior-модели

Дата: 2026-09-03. Репозиторий задачи: `G:\Android\AndroidStudioProjects\anwapvideoplayer`
(реальная жалоба пользователя, не синтетический пример). MCP-сервер:
`g:\AIModels\MCPs\local-junior` (коммиты `c9b70b1`, `54a0652`, `6ad7aad`, +retry в этой
сессии). Junior: Qwen3-27B IQ4_XS, `n_ctx=65536`, профиль `junior-v1`.

## Задача

Жалоба: "при обновлении главного экрана ничего не меняется, список такой же".

**Диагностика (senior, я)**: прочитал `HomeFragment`/`HomeViewModel`/`UiAction`, проверил
через `local_find` трассировку refresh-флоу. Первая гипотеза (что `distinctUntilChanged`
глотает обновление из-за `triggerId`) — опровергнута чтением `UiAction.kt`
(`triggerId` — часть `data class`, участвует в `equals`). Настоящая причина: путь
"обновить список" (`loadMovies`/`reloadList`) пере-запрашивает **тот же Room** —
`MainPagingSource` читает только локальную БД, а реальное обновление данных идёт
отдельным несвязанным путём (`downloadData`/`dataUpdateInteractor`). Решение: добавить
pull-to-refresh, подключённый к `downloadData(force = false)`.

Это разделение принципиально: **диагностика и решение — работа senior**, она заняла
почти всё время и не делегировалась. Делегирована только реализация уже принятого
решения — ровно по правилу из SKILL.

## Методология замера

- **Плечо A**: senior пишет полную реализацию текстом (как обычно).
- **Плечо B**: senior пишет только Change Contract, исполняет через `local_implement`,
  затем пишет review-вердикт по итоговому diff.
- Токены считаны через `/tokenize` локальной модели (её токенайзер, не Claude —
  абсолютные числа условны, но соотношение A/B показательно).
- Отдельную senior-модель прогнать через API не удалось (`ANTHROPIC_AUTH_TOKEN=dummy`
  в этом окружении); тратить чужие ключи без разрешения не стал. Senior — я сам,
  дисциплинированно: в A не облегчал себе задачу, в B не сокращал контракт искусственно.

## Путь до этого результата — тоже часть ответа

Первый прогон на этой же задаче **упал** (`fetch failed` — сервер уронил переполненный
контекст). Второй — **упал иначе** (compile failed: не хватало `secrets.properties` в
изолированном worktree, а repair-loop бессмысленно потратил на это все 3 попытки).
Третий — упал на разовом `ECONNRESET`. Только четвёртый, после трёх раундов
инженерных фиксов рантайма (context-guard на основе `n_ctx` из `/props`,
baseline fail-fast для инфраструктурных проблем, копирование gitignored build-конфига в
worktree, retry на transient сетевые ошибки, устойчивость к исключениям без потери уже
сделанной работы), — дошёл до `completed`.

Это не минус для junior-модели — модель сама, когда до неё доходило дело, писала
корректный код с первого раза. Все четыре падения были **инфраструктурными** (бюджеты,
конфиги, сеть), не смысловыми ошибками модели. Но это значит: **junior как MCP-сервис
без этого слоя инженерии непригоден** — сырой `local_implement` без machine-enforced
бюджетов, baseline-проверки окружения и retry регулярно возвращал бы неинформативные
падения вместо результата.

## Вердикт

**Да, локальная модель способна быть junior-помощником senior-модели** — но только
внутри рантайма, который:

1. сам считает бюджеты (шаги, tool calls, файлы, оценка размера контекста) и
   принудительно финализирует до того, как сервер уронит запрос;
2. сам проверяет факты (compile/tests/scope через реальные команды, а не слова модели);
3. отделяет инфраструктурные проблемы от проблем в коде (baseline fail-fast — не жечь
   repair-бюджет на то, что junior не может починить);
4. переживает единичные сетевые сбои (retry) и не теряет уже сделанную работу при
   исключении;
5. сериализует доступ к единственному слоту модели между процессами (лок), когда её
   спрашивают из нескольких мест одновременно.

При соблюдении этих условий: **на задаче с уже принятым решением и понятным scope,
junior выдал функционально идентичный код за 29% меньше output-токенов senior**
(без учёта времени — сам прогон занял ~1-6 минут на попытку, что для non-interactive
delegated work приемлемо).

**Условие применимости**: правило из SKILL подтвердилось на практике — делегировать
можно только когда решение уже принято и выразимо контрактом с проверяемыми критериями.
Диагностика (поиск настоящей причины бага) осталась полностью на senior и заняла
основное время; это ожидаемо и не должно делегироваться.
