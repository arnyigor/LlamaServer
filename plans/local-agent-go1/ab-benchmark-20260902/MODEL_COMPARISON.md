# Сравнение моделей на одном и том же контракте: Qwen3-27B IQ4_XS vs Ornith-1.5-9B Q8_0

Тот же Change Contract (pull-to-refresh в `anwapvideoplayer`, см. `VERDICT.md`), тот же
MCP-рантайм (`local_implement`), тот же профиль лимитов (steps/tool_calls/repairs).
Единственная переменная — модель.

| | Qwen3-27B IQ4_XS (`junior-v1`) | Ornith-1.5-9B Q8_0 (`ornith-9b-v1`) |
|---|---|---|
| n_ctx | 65536 | 131072 |
| Параметров | 27B | 8.95B |
| Итоговый статус | `completed` | `worker_error` |
| f_home.xml (265 строк) | ✅ корректно, точечный edit | ✅ корректно, точечный edit — **идентичен** Qwen построчно |
| HomeFragment.kt (1108 строк) | ✅ корректно, точечные edit_file | ❌ не применён вообще |
| Compile | pass | pass (потому что второй файл не тронут — неполное решение всё ещё компилируется) |
| search: SwipeRefreshLayout | pass | pass |
| search: swipeRefresh (в .kt) | pass (5 совпадений) | **fail (0 совпадений)** |
| Время | ~1-6 мин (после фиксов рантайма) | ~12 мин |
| Repair attempts | 2 из 3 | 2 из 3 (оба провалились одинаково) |

## Что именно пошло не так у слабой модели

На маленьком файле (`f_home.xml`, 265 строк) Ornith-9B сделала **точно такую же**
точечную правку, как Qwen-27B — через `edit_file` с уникальным `old_string`. Проблем
не было.

На большом файле (`HomeFragment.kt`, 1108 строк) модель не смогла сформулировать
достаточно узкий и уникальный `old_string` для `edit_file` в нужных 4 местах (listener,
3 места в LoadStateListener, onPause) и вместо этого попыталась **переписать файл
целиком через `write_file`** — то есть регенерировать все 1108 строк с одной вставленной
правкой. Итоговый tool-call argument (~40+ KB экранированного Kotlin-кода) сломал
JSON-парсинг на стороне сервера:

```
HTTP 500: Failed to parse tool call arguments as JSON:
parse error at line 1, column 40497: syntax error while parsing value -
invalid string: missing closing quote
```

Это повторилось **дважды** (обе repair-попытки), после чего runtime корректно
остановился (`workerErrors.length > 0 → break`, работа на диске не потеряна, вернулся
честный `status: worker_error` вместо тихого зависания или потери прогресса).

## Интерпретация

Это не баг рантайма — это **граница возможностей модели**. Более слабая модель:

1. Не удержала достаточно точный instruction-following, чтобы найти уникальный,
   компактный фрагмент для `edit_file` в большом файле — и выбрала более "простой" по
   форме, но неверный по факту путь (переписать всё).
2. Наткнулась на побочный лимит: очень длинные tool-call аргументы (полный файл в
   одной JSON-строке) ломают парсер llama.cpp сервера на определённом размере. Это
   отдельный, ортогональный найденный лимит — стоит иметь в виду при работе с любой
   моделью на больших файлах, не только со слабыми.

При этом там, где задача была маленькой и локальной (XML), результат неотличим от
топ-модели. Это согласуется с общим правилом делегирования: **размер и точность
требуемого изменения имеют значение сами по себе**, независимо от того, решение уже
принято или нет.

## Практический вывод для routing rule

Уточнение к правилу из SKILL: для junior-моделей меньшего размера имеет смысл **дробить
allowed_files по размеру файла** — контракт с изменением в файле на 1000+ строк стоит
либо разбивать на несколько более узких под-контрактов (по одному logical change за
раз), либо не делегировать вовсе слабой модели, только сильной. Для Qwen3-27B такого
ограничения на этой задаче не потребовалось.

## Вывод по вопросу "способна ли локальная модель быть junior-помощником"

Ответ теперь калиброван по размеру модели, а не абсолютен:

- **Qwen3-27B IQ4_XS**: да, безоговорочно на этой задаче (byte-for-byte идентичный
  результат, 29% экономии токенов senior).
- **Ornith-1.5-9B Q8_0**: да **частично** — справилась с простой точечной правкой
  небольшого файла, не справилась с многоместной правкой большого файла. Runtime
  корректно задетектировал и остановил проблему, не потеряв частичный прогресс и не
  повредив рабочее дерево — то есть даже при провале worker'а система вела себя
  безопасно (ключевое инженерное требование подтвердилось на негативном случае).

Практическая рекомендация: для 9B-класса моделей imеет смысл **явно ограничивать размер
файла в allowed_files** контракта (например, отклонять контракт runtime'ом, если файл
> N строк, до того как звать модель) — это ещё один потенциальный machine-enforced guard
уровня "P0", по аналогии с baseline fail-fast.
